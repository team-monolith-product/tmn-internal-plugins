# Operational Postmortem

목표는 긴 반성문이 아니라 `사건 → 원인 조사 → 바꿀 시스템 지정 → 개선 작업 → 사용자 리뷰 → 완료`가 실제로 이어지는 폐쇄형 개선 루프입니다.

작업 완료 단계에서 이 스킬을 항상 실행하되, 모든 작업에 포스트모템 글을 만들지는 않습니다. 기대와 실제의 차이, 잘못된 전제, 불필요한 작업, 의미 있는 재작업, 검색·맥락 회수 실패, 착수 조건 누락, 도구·검증 실패가 없으면 `no_postmortem`으로 반환합니다.

## 조사 원칙

현재 대화, `start-slack-list-task`가 반환한 요청 맥락과 작업 기록, 실제 산출물·검증 결과를 먼저 대조합니다. 필요한 과거 기록은 `query_knowledge`로 다시 조사합니다.

분석 중에는 아래를 서로 섞지 않습니다.

- 확인된 사실
- 아직 확인되지 않은 가설
- 기대했던 결과와 실제 결과
- 실패를 만든 결정부터 결과까지의 인과관계
- 당시에 이용 가능했지만 놓친 신호와 선행 조건
- 정확한 원인을 밝히기 위해 추가로 조사할 사항
- 개인의 주의가 아니라 절차·스킬·검색·도구·자동화로 바꿀 수 있는 부분

원인을 모르면 그럴듯한 문장으로 메우지 않습니다. 예를 들어 과거 자료를 못 찾은 사건은 다음 가능성을 구분해 확인합니다.

- 검색 자체를 수행하지 않았는가
- 정확한 업무명 하나만 쓰고 동의어·현장 표현·산출물 이름을 놓쳤는가
- 관련 Slack 스레드, 첨부파일 또는 문서가 수집·검색 대상에서 빠졌는가
- 권한이나 링크 오류로 읽지 못했는가
- 작업 생성 맥락에 과거 기록과 원문 링크가 연결되지 않았는가

도구 기록이나 검색 범위를 확인할 수 없으면 `검색하지 않았다`고 단정하지 않고 가설과 추가 조사로 남깁니다. 검색 결과가 없다는 사실도 원문 부재, 색인 누락, 표현 불일치 중 무엇인지 확인하기 전에는 원인이 아닙니다.

## 착수 조건 실패 확인

작업이 기술적으로 가능했는지만 보지 말고 그 시점에 필요했는지도 확인합니다. 신청자, 운영 방식, 외부 양식, 승인, 입력 데이터처럼 산출물의 필요성과 형태를 결정하는 선행 조건이 없었다면 별도의 실패 원인으로 다룹니다.

과거 기록 회수 실패와 착수 조건 판단 실패처럼 독립적인 인과관계가 둘 이상이면 합쳐서 하나의 모호한 원인으로 만들지 않습니다. 각각의 확인된 사실, 가설, 추가 조사, 개선 대상을 구분합니다.

## 포스트모템 위치

포스트모템은 문제가 발견된 곳이 아니라 실패를 유발한 결정이 내려진 곳에 남깁니다.

- 요청·전제·기획·작업 생성이 원인이면 해당 `source_threads`의 스레드
- 수행·도구 사용·검증이 원인이면 `work_thread`
- 양쪽에 원인이 있으면 주된 원인의 스레드에 원문을 남기고 다른 스레드에는 원문 링크만 남김

`publish-operational-postmortem`의 `target_thread_url`에는 선택한 원인 스레드 permalink를, 필요할 때만 `related_thread_url`에는 다른 스레드 permalink를 전달합니다. 연결되지 않은 채널이나 별도 포스트모템 채널을 만들지 않습니다.

## 개선 작업 판단

`다음에는 주의한다`를 개선안으로 쓰지 않습니다. 확인된 원인 또는 명시적인 조사 가설에 따라 다음 중 실제로 바꿀 대상을 고릅니다.

- 시기상조이거나 불필요한 작업을 만들지 않고 `대기`시키는 생성·착수 규칙
- 작업 생성 맥락에 과거 기록과 원본 자료를 연결하는 절차
- 작업 시작 스킬의 검색어 확장, 검색 범위, 확인 질문
- 선행 조건이 충족되지 않으면 착수하지 않는 가드레일
- 반복 가능한 검증 규칙이나 자동화
- 원인이 확인된 뒤에만 필요한 기능

기능 개발을 기본 해결책으로 삼지 않습니다. 절차나 스킬 수정으로 충분하면 가장 작은 변경을 작업으로 만듭니다.

실제로 조사하거나 변경할 후속 조치가 있을 때만 `improvement_task_title`을 전달합니다. 이 경우 다음도 반드시 전달합니다.

- `improvement_target`: 바꿀 스킬, 워크플로, 도구 또는 운영 절차
- `hypotheses`: 아직 확인되지 않은 원인
- `investigation_items`: 무엇을 더 조사해야 하는지
- `completion_criteria`: 조사 또는 변경이 끝났다고 판단할 관찰 가능한 기준

도구는 이 경우에만 Slack 글에 `@자동화`를 표시하고 원 작업과 같은 Slack List에 `대기` 작업을 만듭니다. 새 작업의 요청 맥락과 작업 기록은 포스트모템이 있는 스레드로 연결되므로, 개선 작업 결과도 그 스레드에 게시되고 현재 대화에서 사용자 리뷰를 받은 뒤 완료됩니다.

## 게시

깊은 분석 전체를 Slack에 복사하지 않습니다. 사건에 필요한 항목만 `publish-operational-postmortem`에 전달합니다.

- `incident_key`: 같은 사건의 재시도에서 바뀌지 않는 짧은 식별자
- `title`: 실패를 만든 핵심 결정 또는 시스템 문제
- `expected`, `actual`: 기대와 실제
- `confirmed_causes`: 근거가 확인된 원인만
- `hypotheses`: 아직 확인되지 않은 원인만
- `missed_signals`: 당시 이용 가능했던 신호와 선행 조건
- `investigation_items`, `system_changes`: 필요한 것만
- `references`: 실제로 사용한 원문 링크. 항상 마지막에 표시됨

확인된 원인이 하나도 없어도 조사 가치가 있는 구체적인 가설과 완료 기준이 있으면 조사 작업을 만들 수 있습니다. 반대로 바꿀 일도 조사할 일도 없으면 `@자동화`와 개선 작업을 만들지 않습니다.

게시 성공 뒤 원문 permalink와 개선 작업 링크를 완료 호출자에게 반환합니다. 실패하면 게시·작업 생성이 끝났다고 주장하지 않습니다.
