# Start Operate Task

Slack은 에이전트 대화를 중계하는 곳이 아니라 다음 사람이 다시 쓸 조직 기억을 남기는 곳입니다.

이 스킬은 운영팀 작업 생명주기에만 적용합니다. 플러그인에 함께 포함된 전사 지식 검색은 작업에 필요한 사내 맥락을 찾을 때 사용할 수 있지만, 일반적인 지식 검색만으로 Slack 작업을 시작하거나 결과를 게시하지 않습니다.

## 시작

1. 사용자가 준 Slack List 작업 행 URL을 `start-slack-list-task`에 전달합니다.
2. 반환된 List 필드에서 완료 여부·담당자·마감일을 확인하고, `source_threads`와 기존 `work_thread`를 읽어 요청 배경, 앞선 선택과 결과, 남은 작업을 파악합니다.
3. `작업 기록` 열이 없다는 오류가 나오면 message 타입의 `작업 기록` 열을 List에 한 번 추가하도록 안내합니다. 다른 열을 대신 쓰지 않습니다.
4. 새 작업 스레드가 필요한 행은 `요청 맥락`에 유효한 Slack 메시지 링크가 있어야 합니다. 이 링크의 채널에 작업 스레드를 만들므로, 링크가 없거나 깨졌다는 오류가 나오면 원본 Slack 메시지를 먼저 연결하도록 안내합니다.
5. 기존 작업 스레드가 있으면 새 스레드를 만들지 않고 재사용합니다. 이 경우 요청 맥락이 없거나 깨졌더라도 경고를 확인한 뒤 기존 작업 기록으로 이어갈 수 있습니다.
6. 이후의 탐색, 질문, 수정, 의사결정은 현재 Claude·Codex 대화 안에서 계속합니다.

## 실행 전 조사 게이트

Slack 작업 연결은 실행이 아닙니다. 실제 판단·문서 작성·데이터 변경에 착수하기 전에 아래 조건을 모두 충족합니다.

1. 작업 제목, 요청 맥락, 기존 작업 기록에서 핵심 사업명·업무명·고유 명사를 뽑습니다.
2. `query_knowledge`를 최소 한 번 호출해 비슷한 이전 작업, 이미 정한 규칙, 반복되는 주의사항을 조사합니다. 정확한 제목으로 결과가 없으면 핵심어를 줄이거나 유사 표현으로 다시 찾습니다.
3. 검색 결과를 현재 요청과 대조해 재사용할 결정, 충돌하는 정보, 아직 모르는 조건을 구분합니다. 결과가 없었다면 없었다는 사실도 현재 판단에 반영합니다.
4. 범위·일정·장소·운영 방식·외부 커뮤니케이션처럼 결과를 바꿀 모호점이 남으면 현재 대화에서 작업 시작자에게 구체적으로 질문하고 답을 기다립니다. 질문과 답변을 Slack 작업 스레드에 중계하지 않습니다.
5. 과거 기록을 검토했고 중요한 모호점이 해소된 뒤에만 실제 작업을 시작합니다.

지식 검색으로 이미 답이 확인되거나 안전하게 되돌릴 수 있는 세부 구현 선택까지 반복해서 묻지는 않습니다.

## Slack에 남기지 않는 것

- 매 응답과 일반 대화
- 도구 호출, 명령어, 원문 로그
- 금방 폐기한 가설과 일상적인 수정 과정
- 내부 추론, 비밀값, 로컬 절대경로
- 작업이 계속될 예정인 상태에서의 중간 진행 보고

## 종료 결과 게시

실제 업무가 완료됐거나, 이번 실행이 막힘·인계로 끝나 다음 사람이 이어받아야 할 때만 `publish_slack_task_result`를 한 번 호출합니다. 단순히 답변 한 번을 마치거나 사용자 입력을 기다리는 것은 종료가 아닙니다.

- `summary`: 무엇이 달라졌는지 독립적으로 이해할 수 있는 결과
- `learnings`: 중요한 시행착오·경험이 있을 때만 0~3개
- `reusable_findings`: 다음 작업에서도 적용할 규칙·사실
- `outputs`: 작업 중 만든 PR, 문서, 시트 등의 `https://` 공유 링크 전체. 만든 링크가 없을 때만 빈 배열
- `validation`: 확인한 동작과 검증 결과
- `remaining`: 미완료 항목, 위험, 인계 사항

완료된 작업은 특별한 이유가 없으면 `status=completed`, `mark_completed=true`로 List도 완료 처리합니다. 막힘이나 인계 상태에서는 완료 처리하지 않습니다.

## 시행착오·경험의 적정선

다시 같은 일을 할 사람이 접근을 바꿀 정보만 적습니다. 보통 비자명한 작업에는 1~2개면 충분하고, 단순 작업은 0개여도 됩니다.

포함할 만한 내용:

- 처음 시도한 방법이 숨은 제약 때문에 실패해 최종 접근을 바꾼 경우
- 문서에 잘 드러나지 않는 API·업무 규칙을 실제로 확인한 경우
- 다음 작업에서 같은 실패나 불필요한 탐색을 줄일 판단 기준

각 항목은 한두 문장으로 `시도·관찰 → 조정한 방법이나 배운 점`이 드러나게 씁니다. 시간순 작업 일지나 사소한 오류 목록은 만들지 않습니다.

게시가 성공하면 최종 사용자 답변에 작업 스레드 permalink를 포함합니다. 게시가 실패하면 Slack에 기록됐다고 주장하지 말고 실패 이유를 알립니다.
