# Start Operate Task

Slack List 체크박스가 작업 상태의 원장입니다. 미체크는 `대기`, 체크는 `완료`이며 다른 상태를 만들지 않습니다. 작업 중 대화와 수정은 현재 Claude·Codex 대화에서 진행하고, Slack에는 시작 연결과 승인된 완료 결과, 필요한 포스트모템만 남깁니다.

이 스킬은 운영팀 작업 생명주기에만 적용합니다. 플러그인에 함께 포함된 전사 지식 검색은 작업에 필요한 사내 맥락을 찾을 때 사용할 수 있지만, 일반적인 지식 검색만으로 Slack 작업을 시작하거나 결과를 게시하지 않습니다.

## 시작

1. 사용자가 준 Slack List 작업 행 URL을 `start-slack-list-task`에 전달합니다. 새 작업이면 봇이 `작업을 시작합니다.`와 작업 링크를 루트 메시지로 남기고, 첫 댓글에는 시작자(Slack 멘션, 매핑할 수 없을 때만 이메일)와 시작 시각만 표시합니다. 실행 도구는 시작 댓글에 쓰지 않습니다.
2. 반환된 List 필드에서 완료 여부·담당자·마감일을 확인하고, `source_threads`와 기존 `work_thread`를 읽어 요청 배경, 앞선 선택과 결과, 남은 작업을 파악합니다.
3. `작업 기록` 열이 없다는 오류가 나오면 message 타입의 `작업 기록` 열을 List에 한 번 추가하도록 안내합니다. 다른 열을 대신 쓰지 않습니다.
4. 새 작업 스레드가 필요한 행은 `요청 맥락`에 유효한 Slack 메시지 링크가 있어야 합니다. 이 링크의 채널에 작업 스레드를 만들므로, 링크가 없거나 깨졌다는 오류가 나오면 원본 Slack 메시지를 먼저 연결하도록 안내합니다.
5. 기존 작업 스레드가 있으면 새 스레드를 만들지 않고 재사용합니다. 이 경우 요청 맥락이 없거나 깨졌더라도 경고를 확인한 뒤 기존 작업 기록으로 이어갈 수 있습니다. 재개를 알리는 중간 댓글은 남기지 않으며, 종료 결과는 같은 스레드에 이어서 게시합니다.
6. 이후의 탐색, 질문, 수정, 의사결정은 현재 Claude·Codex 대화 안에서 계속합니다.

## 실행 전 조사 게이트

Slack 작업 연결은 실행이 아닙니다. 실제 판단·문서 작성·데이터 변경에 착수하기 전에 아래 조건을 모두 충족합니다.

1. 작업 제목, 요청 맥락, 기존 작업 기록에서 사업명·업무명·고유 명사·산출물 유형·핵심 요구사항을 뽑습니다.
2. `query_knowledge`를 반복 사용해 다음 관점을 각각 조사합니다: 같은 사업과 동일 업무, 다른 유사 사업의 같은 업무 패턴, 관련 요구사항·결정·실패 사례.
3. 정확한 이름으로 시작하되 결과가 적으면 핵심어, 유사 표현, 산출물 유형, 상위 업무 범주로 넓힙니다. 새 검색이 이미 본 자료와 결론만 반복할 때까지 탐색합니다.
4. 찾은 기록에서 재사용할 결정과 이유, 요구사항, 실수 방지 규칙, 현재 요청과 충돌하는 정보를 뽑아 실제 계획과 결과물에 반영합니다. 검색 호출 자체로 조사 완료를 간주하지 않습니다.
5. 정확한 업무명으로 결과가 없으면 동의어, 현장 표현, 산출물 이름, 상위 업무 범주로 넓힙니다. 한 표현의 검색 결과만으로 과거 기록이 없다고 결론 내리지 않습니다.
6. 연결된 원문 스레드, 문서·첨부파일, 검색 권한과 수집 범위를 실제로 확인했는지 구분합니다. 읽지 못한 자료는 `없음`이 아니라 `확인되지 않음`입니다.
7. 그래도 관련 기록을 찾지 못하면 현재 대화에서 작업 시작자에게 `관련된 이전 작업·문서·채널과 현장에서 쓰던 표현이 따로 있나요?`라고 묻고 답을 기다립니다.
8. 신청자, 운영 방식, 외부 양식, 승인처럼 산출물의 필요성과 형태를 결정하는 선행 조건이 충족됐는지 확인합니다.
9. 선행 조건이 없거나 아직 작업할 시점이 아니면 추측으로 산출물을 만들지 않습니다. 이유와 확인할 사항을 현재 대화에서 설명하고 Slack List는 `대기`로 둡니다.
10. 과거 기록과 착수 조건을 충분히 검토하고 중요한 모호점이 해소된 뒤에만 실제 작업을 시작합니다.

조사에 실제 사용한 자료 이름과 원문 링크는 작업 동안 누적합니다. 중간 Slack 댓글로 게시하지 않고, 사용자가 완료를 승인했을 때 최종 결과의 마지막 상세 영역에 한 번만 전달합니다.

지식 검색으로 이미 답이 확인되거나 안전하게 되돌릴 수 있는 세부 구현 선택까지 반복해서 묻지는 않습니다.

## 진행 중 재조사 게이트

초기 조사로 작업 전체를 끝내지 않습니다. 아래 변화가 생기면 변경된 방향으로 작업하기 전에 `query_knowledge` 조사를 다시 수행합니다.

- 추가 요구사항이나 예외가 생김
- 범위·방향·대상·산출물·일정·외부 커뮤니케이션이 바뀜
- 새로운 사업명·기관·인물·자료·시스템·제약이 등장함
- 새 정보가 기존 가정이나 결정과 충돌함

재조사할 때는 이전 검색 결과를 버리고 처음부터 반복하지 말고, 새로 생긴 개념과 기존 사업 맥락을 함께 검색합니다. 직접 관련 기록에서 시작해 유사 사업·업무 패턴과 요구사항·결정·실패 사례로 넓히고, 결과에서 발견한 관련 고유 명사와 출처도 이어서 추적합니다. 검색 횟수가 아니라 관련 범위의 커버리지를 최대화하며, 서로 다른 출처에서 새로운 사실·결정·주의사항이 더 나오지 않을 때 멈춥니다. 그래도 관련 자료가 없으면 작업 시작자에게 기존 레퍼런스의 존재와 위치를 다시 확인합니다.

각 재조사에서 실제로 사용한 자료도 기존 목록에 누적합니다. 같은 원문 링크는 한 번만 남깁니다.

## 완료 판단

결과가 준비돼도 바로 완료하지 않습니다. 현재 대화에서 사용자에게 결과와 중요한 제한을 보여 주고 리뷰를 요청합니다. 사용자가 명시적으로 `완료`하라고 한 뒤 아래 조건을 모두 확인해야 완료 단계로 넘어갑니다.

1. 요청한 산출물이나 변경이 실제로 끝났고, 약속한 범위가 충족됐습니다.
2. 결과가 맞는지 확인할 수 있는 검증을 마쳤습니다.
3. 결과를 바꾸는 사용자 승인·결정, 외부 시스템 처리, 필수 입력 대기가 남아 있지 않습니다.

조건이 남아 있으면 이유를 현재 대화에서 설명하고 Slack List는 `대기`로 둡니다. 작업 상태는 `대기`와 `완료`뿐이며 `막힘`이나 `인계` 상태를 만들지 않습니다.

## 완료 단계

사용자의 완료 승인 뒤 다음 순서를 지킵니다.

1. 같은 플러그인의 `$tmn-operating:operational-postmortem`을 반드시 실행해 잘못된 전제, 불필요한 재작업, 검색·맥락 회수 실패, 착수 조건 누락, 도구·검증 실패가 있었는지 검토합니다.
2. 스킬이 `no_postmortem`으로 판단하면 별도 Slack 글 없이 진행합니다.
3. 포스트모템이나 개선 작업이 필요하면 실패를 유발한 결정이 내려진 요청 맥락 또는 작업 기록 스레드에 게시합니다. 개선 작업이 필요한데 게시·생성이 실패하면 원 작업을 완료하지 않습니다.
4. `publish_slack_task_result`를 `user_approved_completion=true`로 한 번 호출해 짧은 결과를 게시하고 List를 완료 처리합니다.
5. 성공하면 최종 사용자 답변에 작업 결과 permalink를 포함합니다.

## Slack에 남기지 않는 것

- 매 응답과 일반 대화
- 중간 참고 자료 기록
- 개별 도구 호출 로그, 명령어, 원문 로그
- 금방 폐기한 가설과 일상적인 수정 과정
- 내부 추론, 비밀값, 로컬 절대경로
- 사용자 리뷰 전 결과와 대기 상태 보고

## 종료 결과 게시

사용자의 완료 승인과 포스트모템 검토를 통과했을 때만 `publish_slack_task_result`를 `user_approved_completion=true`로 호출합니다. 이 도구 호출 자체가 완료를 뜻하며 List 체크박스를 완료로 바꿉니다.

- 기본 결과는 중요한 현재 결과·다음 행동을 담은 `summary`와 이름이 붙은 `outputs`만 사용합니다.
- `summary`는 작업 과정보다 결과가 무엇을 의미하고 다음에 무엇을 해야 하는지 씁니다. `PDF를 제작했습니다`보다 `컨소사에 공유가 필요합니다`가 낫습니다.
- `outputs`의 각 항목은 `산출물 이름: https://공유링크` 형식으로 작성합니다. 만든 공유 산출물이 없을 때만 빈 배열을 사용합니다.
- `검증`, `재사용할 정보`, `시행착오`, `남은 일`을 고정 섹션으로 넣지 않습니다. 실패에서 시스템 개선이 필요한 내용은 별도 포스트모템에 남깁니다.
- `references`에는 실제 판단에 사용한 참고 자료 전체를 `자료 이름: https://원문링크` 형식으로 중복 없이 전달합니다. 참고 자료는 메시지 마지막 상세 영역에 한 번만 표시됩니다.
- 당연한 선택, 통상적인 품질 확인, 사소한 산술, 작업 과정, List에 이미 보이는 상태는 적지 않습니다.

서버는 실행 도구와 작업 스레드 시작 시각부터 종료 게시 시각까지의 전체 시간을 자동으로 기록합니다. 현재 실행 환경에서 직접 확인한 값이 있으면 `publish_slack_task_result`의 `model`, `reasoning_effort`, `input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens`, `total_tokens`, `conversation_turns`에 전달합니다. 확인할 수 없는 값은 생략하며 모델 설정 파일, 기본값, 대화 내용으로 추정하지 않습니다. 생략된 값은 `수집되지 않음`으로 표시됩니다.

종료 메시지의 실행 도구·모델·Effort·토큰·전체 시간·대화 턴과 참고 자료는 하나의 `상세 기록` 영역에 모입니다. 이 영역은 Slack의 `expand=false` section으로 본문과 분리해 가능한 한 접힌 상태로 표시하고, 결과·산출물 본문에는 메타 정보를 반복하지 않습니다.

게시가 성공하면 최종 사용자 답변에 작업 스레드 permalink를 포함합니다. 게시가 실패하면 Slack에 기록됐다고 주장하지 말고 실패 이유를 알립니다.
