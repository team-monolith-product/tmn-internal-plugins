# Start Operate Task

Slack은 에이전트 대화를 중계하는 곳이 아니라 다음 사람이 다시 쓸 조직 기억을 남기는 곳입니다.

이 스킬은 운영팀 작업 생명주기에만 적용합니다. 플러그인에 함께 포함된 전사 지식 검색은 작업에 필요한 사내 맥락을 찾을 때 사용할 수 있지만, 일반적인 지식 검색만으로 Slack 작업을 시작하거나 결과를 게시하지 않습니다.

## 시작

1. 사용자가 Slack List 작업 행 URL을 주었다면 `start-slack-list-task`에 전달합니다.
2. 작업 시작을 요청했지만 행 URL을 주지 않았다면 `list_slack_task_channels`를 호출합니다. 반환된 채널 이름을 보여주고, 어느 채널의 List에 새 행을 만들지 한 번에 물은 뒤 답을 기다립니다. 사용자의 생성 동의와 채널 선택을 추정하지 않습니다.
3. 사용자가 채널을 선택하고 생성에 동의하면 요청에서 짧고 구체적인 제목을 만듭니다. 사용자가 마감일을 명시했다면 그 날짜를 우선합니다. 명시하지 않았다면 `query_knowledge`로 같은·유사 작업의 선행 기간과 현재 관련 행사의 일정을 조사해 정확한 `YYYY-MM-DD` 마감일을 계산합니다. 예를 들어 과거 다과 주문이 연수 3일 전이었다면 다음 연수 날짜를 찾아 3일 전으로 정합니다. 선행 기간이나 대상 일정의 근거가 부족하거나 충돌하면 사용자에게 마감일을 확인하고 기다립니다.
4. 선택받은 `channel_id`, 제목, 확정된 `due_date`로 `create_slack_list_task`를 한 번 호출하고, 반환된 행 링크를 바로 `start-slack-list-task`에 전달합니다. 생성 뒤 시작이 실패하면 같은 행 링크로 시작만 재시도하며 새 행을 만들지 않습니다. 마감일 조사에 실제 사용한 자료는 잃지 말고 이후 초기 조사 자료에 합칩니다.
5. 새 작업이면 봇이 `작업을 시작합니다.`와 작업 링크를 루트 메시지로 남기고, 첫 댓글에는 시작자(Slack 멘션, 매핑할 수 없을 때만 이메일)와 시작 시각만 표시합니다. 실행 도구는 시작 댓글에 쓰지 않습니다.
6. 반환된 List 필드에서 완료 여부·담당자·마감일을 확인하고, `source_threads`와 기존 `work_thread`를 읽어 요청 배경, 앞선 선택과 결과, 남은 작업을 파악합니다.
7. `작업 기록` 열이 없다는 오류가 나오면 message 타입의 `작업 기록` 열을 List에 한 번 추가하도록 안내합니다. 다른 열을 대신 쓰지 않습니다.
8. 유효한 `요청 맥락`이 있으면 그 메시지의 채널에 작업 스레드를 만듭니다. 요청 맥락이 없거나 깨졌으면 해당 List가 등록된 채널에 만들고, 반환된 `source_threads`의 오류를 작업 맥락과 함께 확인합니다.
9. 기존 작업 스레드가 있으면 새 스레드를 만들지 않고 재사용합니다. 이 경우 요청 맥락이 없거나 깨졌더라도 경고를 확인한 뒤 기존 작업 기록으로 이어갈 수 있습니다. 재개를 알리는 중간 댓글은 남기지 않으며, 종료 결과는 같은 스레드에 이어서 게시합니다.
10. 이후의 탐색, 질문, 수정, 의사결정은 현재 Claude·Codex 대화 안에서 계속합니다.

## 실행 전 조사 게이트

Slack 작업 연결은 실행이 아닙니다. 실제 판단·문서 작성·데이터 변경에 착수하기 전에 아래 조건을 모두 충족합니다.

1. 작업 제목, 요청 맥락, 기존 작업 기록에서 사업명·업무명·고유 명사·산출물 유형·핵심 요구사항을 뽑습니다.
2. `query_knowledge`를 반복 사용해 다음 관점을 각각 조사합니다: 같은 사업과 동일 업무, 다른 유사 사업의 같은 업무 패턴, 관련 요구사항·결정·실패 사례.
3. 정확한 이름으로 시작하되 결과가 적으면 핵심어, 유사 표현, 산출물 유형, 상위 업무 범주로 넓힙니다. 새 검색이 이미 본 자료와 결론만 반복할 때까지 탐색합니다.
4. 찾은 기록에서 재사용할 결정과 이유, 요구사항, 실수 방지 규칙, 현재 요청과 충돌하는 정보를 뽑아 실제 계획과 결과물에 반영합니다. 검색 호출 자체로 조사 완료를 간주하지 않습니다.
5. 표현과 범위를 바꿔도 관련 기록을 찾지 못하면 현재 대화에서 작업 시작자에게 `관련된 이전 작업·문서·채널이 따로 있나요?`라고 묻고 답을 기다립니다.
6. 범위·일정·장소·운영 방식·외부 커뮤니케이션처럼 결과를 바꿀 모호점도 작업 시작자에게 구체적으로 질문합니다. 질문과 답변은 Slack 작업 스레드에 중계하지 않습니다.
7. 과거 기록을 충분히 검토하고 중요한 모호점이 해소된 뒤에만 실제 작업을 시작합니다.

조사 게이트를 통과하면 작업 생성 전 마감일 조사와 실제 판단·계획·산출물에 사용한 자료를 합쳐 `record_slack_task_references`로 작업 스레드에 한 번 기록합니다. `reason`에는 `초기 조사`처럼 조사 계기를 쓰고, `references`는 `자료 이름: https://원문링크` 형식으로 전달합니다. 검색 결과 전체, 사용하지 않은 자료, SQL·도구 호출 로그는 남기지 않습니다.

지식 검색으로 이미 답이 확인되거나 안전하게 되돌릴 수 있는 세부 구현 선택까지 반복해서 묻지는 않습니다.

## 진행 중 재조사 게이트

초기 조사로 작업 전체를 끝내지 않습니다. 아래 변화가 생기면 변경된 방향으로 작업하기 전에 `query_knowledge` 조사를 다시 수행합니다.

- 추가 요구사항이나 예외가 생김
- 범위·방향·대상·산출물·일정·외부 커뮤니케이션이 바뀜
- 새로운 사업명·기관·인물·자료·시스템·제약이 등장함
- 새 정보가 기존 가정이나 결정과 충돌함

재조사할 때는 이전 검색 결과를 버리고 처음부터 반복하지 말고, 새로 생긴 개념과 기존 사업 맥락을 함께 검색합니다. 직접 관련 기록에서 시작해 유사 사업·업무 패턴과 요구사항·결정·실패 사례로 넓히고, 결과에서 발견한 관련 고유 명사와 출처도 이어서 추적합니다. 검색 횟수가 아니라 관련 범위의 커버리지를 최대화하며, 서로 다른 출처에서 새로운 사실·결정·주의사항이 더 나오지 않을 때 멈춥니다. 그래도 관련 자료가 없으면 작업 시작자에게 기존 레퍼런스의 존재와 위치를 다시 확인합니다.

각 재조사가 끝날 때도 변경된 판단에 실제 사용한 자료를 `record_slack_task_references`로 한 번 기록합니다. 이전 게이트에서 이미 쓴 자료라도 이번 변경 판단에 다시 사용했다면 포함할 수 있습니다. 종료 결과를 위해 작업 전체에서 사용한 참고 자료의 이름과 원문 링크를 누적해 둡니다.

## 완료 판단

사용자가 꼭 "완료"라고 말할 필요는 없습니다. 에이전트는 아래를 모두 확인했을 때만 작업을 완료로 선언합니다.

1. 요청한 산출물이나 변경이 실제로 끝났고, 약속한 범위가 충족됐습니다.
2. 결과가 맞는지 확인할 수 있는 검증을 마쳤고, 그 근거를 `validation`에 남길 수 있습니다.
3. 결과를 바꾸는 사용자 승인·결정, 외부 시스템 처리, 필수 입력 대기가 남아 있지 않습니다.

단순히 답변을 한 번 보냈거나 사용자의 답을 기다리는 상태는 종료가 아니므로 결과를 게시하거나 List를 완료 처리하지 않습니다. 사용자가 명시적으로 열어 두라고 하면 완료 결과여도 `mark_completed=false`를 사용합니다.

## Slack에 남기지 않는 것

- 매 응답과 일반 대화
- 개별 도구 호출 로그, 명령어, 원문 로그
- 금방 폐기한 가설과 일상적인 수정 과정
- 내부 추론, 비밀값, 로컬 절대경로
- 작업이 계속될 예정인 상태에서의 중간 진행 보고

조사 게이트에서 남기는 선별된 참고 자료 기록은 중간 진행 보고가 아니라 판단 근거 로그이므로 예외입니다.

## 종료 결과 게시

실제 업무가 완료됐거나, 이번 실행이 막힘·인계로 끝나 다음 사람이 이어받아야 할 때만 `publish_slack_task_result`를 한 번 호출합니다. 단순히 답변 한 번을 마치거나 사용자 입력을 기다리는 것은 종료가 아닙니다.

- 기본 결과는 중요한 현재 상태·다음 행동을 담은 `summary`, 이름이 붙은 `outputs`, 다른 사업에서도 재사용할 고가치 정보만 사용합니다.
- `summary`는 작업 과정보다 결과가 무엇을 의미하고 다음에 무엇을 해야 하는지 씁니다. `PDF를 제작했습니다`보다 `컨소사에 공유가 필요합니다`가 낫습니다.
- `outputs`의 각 항목은 `산출물 이름: https://공유링크` 형식으로 작성합니다. 만든 공유 산출물이 없을 때만 빈 배열을 사용합니다.
- `learnings`에는 비슷한 작업에서 반복할 수 있는 주요 실수·숨은 제약과 이를 피하거나 해결한 방법을 씁니다.
- `reusable_findings`에는 다른 사업의 계획·실행·검토에도 적용할 중요한 결정과 이유, 요구사항, 판단 기준을 씁니다.
- 중요한 결정과 재사용 정보는 산출물에 있더라도 스레드에서 바로 찾을 가치가 있으므로 반복해도 됩니다.
- `validation`과 `remaining`은 그 정보가 다음 사람의 판단이나 행동을 실제로 바꿀 때만 사용합니다.
- `references`에는 각 조사 게이트에서 실제로 사용한 참고 자료 전체를 `자료 이름: https://원문링크` 형식으로 중복 없이 전달합니다.
- 당연한 선택, 통상적인 품질 확인, 사소한 산술, 작업 과정, List에 이미 보이는 상태는 적지 않습니다.

서버는 실행 도구와 작업 스레드 시작 시각부터 종료 게시 시각까지의 전체 시간을 자동으로 기록합니다. 현재 실행 환경에서 직접 확인한 값이 있으면 `publish_slack_task_result`의 `model`, `reasoning_effort`, `input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens`, `total_tokens`, `conversation_turns`에 전달합니다. 확인할 수 없는 값은 생략하며 모델 설정 파일, 기본값, 대화 내용으로 추정하지 않습니다. 생략된 값은 `수집되지 않음`으로 표시됩니다.

종료 메시지의 실행 도구·모델·Effort·토큰·전체 시간·대화 턴과 참고 자료는 하나의 `상세 기록` 영역에 모입니다. 이 영역은 Slack의 `expand=false` section으로 본문과 분리해 가능한 한 접힌 상태로 표시하고, 결과·산출물 본문에는 메타 정보를 반복하지 않습니다.

완료된 작업은 특별한 이유가 없으면 `status=completed`로 게시합니다. 이 상태는 기본적으로 List도 완료 처리하고 작업 기록 루트에 `✅` 반응을 남기며, 특별한 이유가 있을 때만 `mark_completed=false`로 유지합니다. 막힘이나 인계 상태에서는 완료 처리하지 않습니다.

게시가 성공하면 최종 사용자 답변에 작업 스레드 permalink를 포함합니다. 게시가 실패하면 Slack에 기록됐다고 주장하지 말고 실패 이유를 알립니다.
